# Сдача результатов: JSON 1.0

Контракт сверён с `CQA_Student_Guide_Appendix_Results.pdf` (3 страницы).
Это отдельная выгрузка для организаторов. Старый `GET /api/v1/datasets/{id}/export`
остаётся полным архивом и **не подходит** вместо файла результатов.

В корне репозитория должны появиться:

- `results/dev/results.json`: 65 исходных диалогов — 60 чатов и 5 звонков;
- `results/prod/results.json`: ровно 10 контрольных чатов, включая ошибки.

Контрольный набор выдаётся за час до стоп-кода. За этот час нужно получить
данные, оценить, проверить JSON, сделать commit **и push**. Папки подготовлены;
официальные файлы ещё нужно подготовить и отправить. В общем `main` есть
Gemini-адаптер. AI-участник описал 65 валидных DEV-оценок в локальных файлах,
но это не подтверждает их наличие в общей БД или публикацию JSON 1.0.
Сохранённые черновики не становятся файлом сдачи после переименования.
Тестовые и ручные оценки нельзя выдавать за результаты модели.

## Проверка готовности перед выгрузкой

Используйте тот же манифест выбора, который затем передадите экспорту. Команда
повторно использует `SubmissionService` и проверку HTTP-выгрузки, не рассчитывает
баллы по отдельной формуле. Она проверяет состав DEV/PROD, полный явный выбор
исходов, завершённость выбранного пакета, исходные AI-оценки, снимки диалогов,
допустимые критерии/веса/шкалы/N/A, цитаты и заявленные модели. Для пакета
проверяется соответствие версии чек-листа пакету. «Последнюю подходящую» оценку
команда не выбирает.

Для alwaysdata — HTTP, из локального клона:

```text
python -m backend.submission_check --api https://replimetr.alwaysdata.net --dataset-id DATASET_UUID --manifest data/submission-dev.json
```

Для собственной локальной SQLite:

```text
python -m backend.submission_check --database data/cqa.sqlite3 --dataset-id DATASET_UUID --manifest data/submission-dev.json
```

После скачивания файла добавьте его сверку и, при необходимости, JSON-отчёт:

```text
python -m backend.submission_check --api https://replimetr.alwaysdata.net --dataset-id DATASET_UUID --manifest data/submission-dev.json --results-file results/dev/results.json --json
```

Для PROD используйте его набор, манифест со `split: "prod"` и путь
`results/prod/results.json`. На Windows можно заменить `python` на
`.venv\Scripts\python.exe`.

| Статус | Код выхода | Значение |
| --- | ---: | --- |
| `export_ready` | 0 | Выбранные исходные оценки проходят экспорт; если файл указан, он совпадает |
| `export_ready_with_errors` | 1 | Формат выгрузки корректен, но есть `status: "error"`; проверьте перечисленные ID |
| `blocked` | 2 | Источник не прошёл проверку, недоступен либо указанный файл некорректен/не совпадает |

JSON-отчёт содержит `can_export`, количества успешных/ошибочных исходов,
`failed_conversation_ids`, `file_status`, код проблемы и время проверки. В нём
нет транскриптов, цитат, ответов модели или текстов ошибок отдельных диалогов.
`file_status: "not_checked"` означает, что файл не проверялся; даже код выхода 0
не утверждает, что `results.json` уже существует. При несовпадении файла
`can_export: true` означает только валидность выбранных результатов в источнике;
общий статус остаётся `blocked`.

Сверка файла учитывает содержимое JSON, игнорируя пробелы и порядок ключей
объектов. Порядок массивов сохраняется; `true` отличается от числа `1`.
Повторные ключи, NaN/Infinity, неверный UTF-8 и JSON более 16 MiB отвергаются.
Файлы не создаются и не перезаписываются. Отчёт можно сохранить перенаправлением
stdout в отдельный файл, например `> data/dev-readiness.json`.

Локальная БД открывается SQLite URI `mode=ro` с `query_only`: нет создания БД,
миграций, запуска обработчика или AI. Для живой базы alwaysdata используйте
**только `--api`**, не открывайте её через SSH/NFS. HTTP-режим делает один запрос
к существующему POST `/api/v1/datasets/{id}/submission`; маршруты API не меняются.
Загруженный JSON проверяется существующим HTTP-клиентом. При `items` сверяются
внешние ID и явные исходы; при `batch_id` происхождение, состав набора и снимки
проверяет сервер, поскольку JSON 1.0 их не содержит. Перенаправлений и повторов нет.
Поддержаны те же переменные Basic Auth, что у `submission_remote`.
`--timeout` задаёт положительный конечный тайм-аут (по умолчанию 30 секунд).

HTTP-ошибка печатается без тела ответа сервера. При 422 проверьте состав набора,
завершённость пакета, выбранные оценки и чек-лист; локальный режим возвращает
конкретную причину общего валидатора. Проверка фиксирует состояние на момент
чтения и не блокирует параллельное возобновление пакета. После изменения выбора
или повторной обработки проверьте файл снова.

**Эта команда не подтверждает точность AI, текущую квоту, отправку Git или срок
сдачи.** Сохранённые результаты можно проверить без доступной модели. Ошибки
разрешены форматом организаторов, но не считаются успешными оценками: не удаляйте
их ID и не заменяйте ошибку нулём. Даже при коде 1 финальную выгрузку можно
сформировать, осознанно сохранив эти ошибки.

## Быстрый путь: завершённый пакет

1. Импортировать набор, сохранить его UUID и исходные `conversation_id`.
2. После подключения реального Evaluator создать пакет на всех внутренних UUID
   набора с `freedom-broker`, версией 1. Получить его `batch_id`.
3. Опросить `GET /api/v1/evaluation-batches/{batch_id}`. Перед экспортом все
   элементы должны быть `succeeded`, `failed` или `interrupted`.
4. Скопировать `examples/submission-batch.json` в `data/submission-dev.json` и
   заполнить `batch_id`, настоящее название команды, режим и имена моделей.
5. Из корня проекта выполнить (на Windows используйте `.venv\Scripts\python.exe`,
   на Linux — `.venv/bin/python` вместо `python`):

```text
python -m backend.submission_cli --database data/cqa.sqlite3 --dataset-id DATASET_UUID --manifest data/submission-dev.json
python -m backend.submission_cli --database data/cqa.sqlite3 --dataset-id DATASET_UUID --manifest data/submission-dev.json --check
```

`split: "dev"` выбирает стандартный путь `results/dev/results.json`; `"prod"` —
`results/prod/results.json`. Для PROD создайте отдельный манифест и укажите UUID
контрольного набора и его пакета. `group_id` не угадывается: способ получения
контрольных данных сообщают организаторы.

Повторная запись существующего результата требует `--overwrite`. Сначала
проверяется весь документ, затем новый UTF-8 файл публикуется атомарно. При
ошибке прежний файл сохраняется. `--check` ничего не записывает, сверяет JSON
с выбранными исходными оценками в БД, отвергает дубли ключей и нечисловые NaN/Infinity.
Можно задать `--output PATH`, но для сдачи используйте именно пути выше.
CLI не запускает веб-сервер, обработчик пакетов или модель.

При приближении дедлайна можно отменить **только pending** через существующий
`POST /api/v1/evaluation-batches/{batch_id}/cancel`. Они экспортируются как
`error: "BATCH_CANCELLED_BEFORE_START"`. Уже выполняющийся платный вызов не
отменяется; до его завершения экспорт пакета вернёт 422. При необходимости
используйте явный список исходов ниже, честно указав причину отсутствия результата.

## API для frontend-участника

### Скачать результат с размещённого backend

Из локального клона, с заполненным существующим манифестом:

```text
python -m backend.submission_remote --api https://replimetr.alwaysdata.net --dataset-id DATASET_UUID --manifest data/submission-dev.json
```

На Windows вместо `python` можно использовать `.venv\Scripts\python.exe`.
`split` в манифесте выбирает `results/dev/results.json` или
`results/prod/results.json`. Поддерживаются оба способа выбора: завершённый
`batch_id` или `items`. Для явной замены добавьте `--overwrite`;
`--output PATH` нужен для репетиций вне сдаваемых папок.

Команда делает один POST к API сдачи, не вызывает модель и не выполняет Git.
Проверяются JSON 1.0, отсутствие повторяющихся JSON-ключей и NaN/Infinity,
имя команды, режим/имена моделей, число и уникальность ID. Для `items` также
сверяются внешние ID, тип исхода и явно переданные ошибки. Исходные оценки,
цитаты, формулу, принадлежность набору и версии проверяет серверный
SubmissionService. Ответ JSON 1.0 не содержит dataset_id/batch_id/evaluation_id:
локально повторно доказать их принадлежность без БД невозможно. При `batch_id`
доверяем этому серверному контракту; автоматического выбора оценки нет.

Тайм-аут сетевого ожидания — 30 секунд (`--timeout SECONDS`), лимит ответа —
16 MiB, проверяется и заголовок, и фактически прочитанные байты. Между блоками
проверяется общий срок загрузки; текущая блокирующая операция чтения ограничена
сетевым тайм-аутом. Перенаправления и автоматические повторы отключены. Для
внешнего сервера обязателен HTTPS; HTTP разрешён только на loopback для теста.
`--api` принимает origin без `/api/v1`, credentials, query и fragment.
Системные proxy/.netrc не используются (`trust_env=False`).

Запись выполняется временным файлом рядом с результатом и атомарной публикацией.
До полной проверки прежний файл сохраняется. Символическая ссылка, входной
манифест и hard-link на него не могут быть выходным файлом. Без `--overwrite`
существующий файл отвергается. Код выхода: 0 — файл сохранён, 2 — ошибка.
`OK` означает успешный экспорт, а не успешную оценку каждого диалога:
проверьте количество `errors` в итоговой строке.

При Basic Auth на reverse proxy CLI читает пару переменных
`CQA_SUBMISSION_HTTP_USER` / `CQA_SUBMISSION_HTTP_PASSWORD` из окружения процесса.
Передавайте их через безопасный ввод/менеджер секретов; пароль не нужен в URL,
аргументах команд, манифесте или frontend. Эти переменные не подключают Gemini.
Настройка доступа описана в [access-control.md](access-control.md).

На alwaysdata не запускайте локальный submission_cli через SSH над живой БД:
используйте HTTP-команду. Локальный `submission_cli --check` остаётся доступен
для собственной локальной БД; HTTP-команда не имеет такого режима.

После проверки настоящих результатов выполните отдельно из корня репозитория:

```text
git add results/dev/results.json
git diff --cached --stat
git commit -m "Add DEV evaluation results"
git push origin main
```

Для PROD замените путь и сообщение коммита. Репетиции с явными ошибками или
тестовыми Evaluator не отправляйте как настоящие результаты модели.
Команды выше предполагают актуальный `main`; перед финальным commit проверьте
ветку через `git branch --show-current` и свои изменения через `git status`.
После push откройте оба нужных файла в удалённом репозитории и зафиксируйте SHA.
Push в Git не обновляет alwaysdata автоматически.

### HTTP-контракт

```http
POST /api/v1/datasets/{dataset_id}/submission
Content-Type: application/json
```

```json
{
  "split": "prod",
  "team_name": "Фактическое название команды",
  "model_mode": "external_api",
  "model_names": ["ACTUAL_MODEL_FROM_METADATA"],
  "batch_id": "BATCH_UUID"
}
```

Ответ 200 — **сам объект организаторского JSON**, без обёртки. Его нужно скачать
как `results.json` и положить в соответствующую папку. Сервер не пишет файлы в Git
и не выполняет push. Маршрут синхронный: FastAPI выполняет SQLite-чтения в пуле
потоков. Ни одного вызова AI экспорт не делает.

Вместо `batch_id` разрешён явный `items` для **каждого** исходного ID набора:

```json
{
  "split": "prod",
  "team_name": "Фактическое название команды",
  "model_mode": "external_api",
  "model_names": ["ACTUAL_MODEL_FROM_METADATA"],
  "items": [
    {"conversation_id": "ORIGINAL_ID_1", "evaluation_id": "EVALUATION_UUID"},
    {"conversation_id": "ORIGINAL_ID_2", "error": "AI_TIMEOUT"}
  ]
}
```

Это сокращённый пример: PROD требует 10 элементов, DEV — 65. `conversation_id`
здесь **внешний ID из API организаторов**, а `evaluation_id` — внутренний UUID
конкретной оценки. Выбор «последней» оценки автоматически не делается.
Нужен ровно один из `evaluation_id` и `error`. В ошибке используйте короткую
причину без ключей, подписанных URL и персональных данных.

Неизвестный набор/пакет — стандартный 404. Неверная полнота, несовместимый
чек-лист, ручная оценка, неверная модель или незавершённый пакет — 422
`INVALID_SUBMISSION`; ошибки формы — 422 `VALIDATION_ERROR`; повреждённые цитаты
и ответы сохраняют прежние коды `INVALID_EVIDENCE` / `INVALID_ANSWER`.

## Что именно преобразуется

| Внутренний ID (API/БД) | ID для сдачи |
| --- | --- |
| contact | contact |
| needs | discovery |
| identity | identification |
| consultation | consultation |
| empathy | empathy |
| management | dialogue |
| closing | closure |
| gross | critical |

- `yes/no/na` превращаются в `true/false/null`. Баллы шкал передаются **до учёта
  веса**: consultation = 0/5/10/15/20, dialogue = 0/4/7/10.
- Для `ok` выгружаются все восемь критериев, каждый ровно один раз.
- `rationale` берётся из исходного объяснения. Каждая цитата повторно сверяется
  с текстом; `evidence_turns` — позиции с 1 во **всём исходном транскрипте**,
  включая клиента, бота и system. Номера не извлекаются из строковых ID сообщений.
- `final_score` пересчитывается существующей Decimal-арифметикой backend:
  N/A исключает вес, итог округляется до двух знаков. Пример из PDF даёт 85.38.
- `critical_flag` соответствует исходному `gross`; флаг не обнуляет итог.
- Экспорт берёт `original`, а не исправленную человеком `final`. Апелляции
  остаются в полном архиве, их изменения не маскируются под результат AI.
- Проверяются снимок разговора, восемь критериев, веса, шкалы и правила
  допустимости N/A. Произвольные чек-листы продолжают работать в обычном API,
  но несовместимый набор правил нельзя случайно сдать в этом формате.
- Тексты разговоров, аудиоссылки, ключи и ручные эталоны в файл не добавляются.
  Объяснения содержат текст автора/модели: перед публичным push просмотрите их.

`model_names` должны перечислять **фактически использованные** модели. Название
каждой успешной AI-оценки сверяется с её сохранёнными metadata. Режим (`local`,
`external_api`, `hybrid`) и сведения о моделях, завершившихся только ошибкой,
указывает команда: нынешние metadata не позволяют проверить их автоматически.
Если модель вообще не подключали, не пишите Gemini как уже использованную и
не сдавайте синтетические фикстуры. Неудачный реальный запуск допустимо
отразить ошибкой для всех ID; это не нулевые оценки и не N/A.

## Последние минуты перед стоп-кодом

1. Сверить исходные ID и полноту каждого набора. Экспорт проверяет БД, но не
   устанавливает подлинность её происхождения без исходного набора организаторов.
2. Выполнить `--check` для DEV и PROD. Просмотреть ошибки и реальные названия моделей.
3. Проверить файлы, затем отправить **оба**:

```text
git add results/dev/results.json results/prod/results.json
git diff --cached --stat
git commit -m "Submit DEV and PROD evaluations"
git push
```

4. Открыть ссылку на отправленную ветку и оба файла, проверить последний commit.
   PDF требует доступность в **открытом репозитории**, ссылка на который передана
   организаторам. Доступность и ветку нужно проверить заранее. Этот функционал
   не меняет видимость репозитория и не публикует результаты автоматически.

Тесты используют только временные синтетические наборы и явно названные
`synthetic-test-only` metadata. Они проверяют формат и backend, а не точность Gemini.
