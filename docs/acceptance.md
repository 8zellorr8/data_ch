# Требования, ручная проверка и недостающие материалы

Сверка на 7 ноября 2026 года, исходная версия backend `6e800c2`. Это план приёмки команды. Непроведённые проверки не отмечены как успешные.

Источники требований: `CQA_Hackathon_Student_Guide_v3 1.pdf` (стр. 1–4), `CQA_Chat_Quality_Checklist 1.pdf` (стр. 1–3) и переданные пользователем уточнения организаторов о звонках и отборе топ-50.

| Материал / возможность | Подтверждённое состояние | Следующее действие |
| --- | --- | --- |
| Исходный гайд и чек-лист | Есть; 8 критериев, веса, шкалы и N/A перенесены в начальную конфигурацию | Использовать одну версию правил для ручной и AI-оценки |

| Набор для frontend | 16 запросов, 38 проверок Postman; OpenAPI и JSON-примеры генерируются скриптом | Подключить интерфейс к этим маршрутам |
| Frontend | В текущем репозитории реализации нет | Участник frontend передаёт рабочий интерфейс и команду запуска |
| AI | Контракт есть, реального провайдера/модели в репозитории нет | Участник AI передаёт адаптер, модель, версию промпта и команду запуска |
| Продуктовый справочник Freedom Broker | В переданных файлах не найден справочник с правилами продуктов и услуг; корпоративная презентация его не заменяет | Получить материалы организаторов и определить, какие факты ими подтверждаются |
| Ручные оценки команды | Файлов разметки и отчёта сравнения в репозитории не найдено | Разметить небольшую выборку; хранить реальные данные и разметку локально |
| Официальный Ground Truth | Команде не предоставлен; в DEV только диалоги, язык, канал и ссылки | Не называть собственную разметку официальным эталоном |
| Контрольные 10 диалогов | В сообщении организаторов заявлены ранее неизвестные транскрипты; в имеющемся DEV это не отдельный контрольный набор | Получить выданный организаторами набор / новое `group_id` в назначенное время |
| Формула рейтинга | Точность относительно Ground Truth — главный ориентир; точная формула агрегирования не дана | Для своей проверки считать несколько прозрачных метрик; уточнить официальный формат результатов |
| Сдача | Есть README; на момент сверки GitHub-репозиторий **private**, гайд требует открытый репозиторий | До сдачи решить доступность репозитория, передать ссылку организаторам и зафиксировать коммит |

Для продолжения backend-разработки контекста достаточно. Для подтверждения готовности всего решения не хватает интеграции, проверки точности и результатов ручной приёмки. Время открытия контроля, точный дедлайн и порядок выступлений сверяются с актуальными объявлениями организаторов: гайд задаёт 23/24 часа от старта, а не абсолютную дату.

## Ручная проверка интерфейса и полного сценария

Проверяющий выполняет действия через готовый интерфейс. До его появления Swagger/Postman позволяют проверить API, но не подтверждают удобство и работоспособность UI. Авторизация для демо по гайду не требуется.

| ID | Действие | Ожидаемый результат | Кто проверяет |
| --- | --- | --- | --- |
| M01 | Запустить по README на втором компьютере / из чистого клона | Понятная установка; backend, frontend и модель запускаются указанными командами | Backend + вся команда |
| M02 | Импортировать новый набор, открыть RU/KZ/EN и звонок | Верные роли, исходные тексты и время; фильтры и страницы работают; звонок открывает запись или плеер | Frontend + backend |
| M03 | Открыть базовый чек-лист и сверить с PDF | 8 критериев; веса 10/15/20/20/15/15/5 и отдельный флаг; шкалы 0/5/10/15/20 и 0/4/7/10 | Backend + AI |
| M04 | Запустить реальную оценку ранее не использованного диалога | Реальный вызов модели, `origin=ai`, версия правил и метаданные сохранены; нет готового ответа по ID | AI + backend |
| M05 | Просмотреть каждый критерий и нажать на цитату | Видны ответ, баллы, вес, объяснение; переход к правильной реплике; `missing` показывает контекст пропуска | Frontend + AI |
| M06 | Проверить N/A и грубое нарушение | Причина N/A соответствует правилу; вес исключён. Флаг отображается отдельно и не обнуляет итог | Вся команда |
| M07 | Создать апелляцию; подтвердить исходное значение | Комментарий, причина решения и цитата доступны; оригинал сохранён; балл остаётся тем же | Frontend + backend |
| M08 | В другой апелляции изменить значение | Итог пересчитан, `revision` выросла, исходная оценка и история решения сохранены | Frontend + backend |
| M09 | Открыть одну оценку в двух вкладках, принять конкурирующие решения | Устаревшая запись получает конфликт; UI перечитывает оценку и не перетирает новое решение | Frontend + backend |
| M10 | **Через UI заменить критерий**, сохранить новую версию и оценить свежий диалог | Изменённое правило реально передано AI; новые поля появились без правки кода; старые оценки используют старую версию | Вся команда |
| M11 | Отключить модель / вызвать недоступность провайдера | Понятная ошибка, нет поддельного успеха; загрузка завершается; импорт и чтение истории доступны | AI + frontend + backend |
| M12 | Экспортировать набор, перезапустить backend, открыть историю | Чек-листы, оригиналы, финальные оценки и апелляции не потеряны; экспорт читается | Backend |
| M13 | Обработать 10 новых диалогов в режиме, выбранном для защиты | Прогресс по каждому, реальные результаты, ошибки видны; измерено общее время | Вся команда |
| M14 | Провести репетицию защиты | За 5 минут показать диалог, доказательство, N/A, апелляцию, изменение критерия и применение новой версии | Вся команда |

**Статус всех M01–M14: ручная приёмка не проведена / не подтверждена в этой работе.** Автоматические тесты и Postman уже проверяли многие backend-сценарии, однако это другой вид проверки. Особенно обязательны M04 и M10: в гайде указана оценка новых транскриптов и замена критерия через интерфейс.

Для каждой проверки сохранить: ID сценария, коммит, версию модели/промпта, ID и версию чек-листа, внутренний ID диалога, ожидаемое и фактическое поведение, PASS/FAIL, проверяющего и дату. Скриншоты с реальными диалогами хранить вне публичного Git. Шаблон записи:

```text
Сценарий: M__
Коммит / окружение:
Модель / промпт:
Чек-лист / версия:
Диалог:
Ожидалось:
Получено:
PASS / FAIL / BLOCKED:
Проверяющий / дата:
Ссылка на локальный результат:
```

## Ручная разметка для проверки точности AI

Это отдельная работа от проверки кнопок и API. Приведённый ниже объём — рекомендация для команды, а не условие организаторов.

1. Выбрать 10–15 DEV-диалогов, охватив RU/KZ/EN, несколько звонков и спорные N/A. Оставить отдельную часть для проверки после настройки промпта; не подбирать промпт по этой части.
2. Двум участникам независимо оценить одни и те же диалоги по фиксированной версии чек-листа. Записать по каждому критерию значение, причину, точную цитату и `message_id`. Разобрать разногласия; при проверке KZ/EN нужен человек, понимающий соответствующий язык.
3. Непроверяемые продуктовые факты отметить как ограничение и запросить источник. Отсутствие справочника **не разрешает N/A**. Для звонков без анализа аудио не выставлять выводы о дикции, темпе или произношении.
4. Сохранить согласованные ручные оценки через `/api/v1/evaluations/manual`, автоматические — через `/api/v1/evaluations`. Сопоставлять один диалог и одну версию правил; ручные оценки не подавать модели при проверке.
5. Посчитать совпадения по каждому критерию, ошибки применения N/A, MAE итогового балла и ошибки флага нарушений отдельно. Зафиксировать число примеров, модель, промпт, время и число вызовов. Это внутренние метрики, а не объявленная формула рейтинга.
6. Посмотреть расхождения вручную: совпадение цитаты с текстом backend проверяет, а её смысловую уместность и правильность консультации оценивают люди / модель. Число пройденных тестов ничего не говорит о точности AI.

- [ ] Получен контрольный набор; результаты обработаны на сдаваемой версии.
- [ ] Доступность репозитория соответствует требованиям; ссылка передана организаторам командой.
- [ ] README содержит запуск всех трёх частей, зафиксирован финальный коммит.
- [ ] Для платной модели указаны название и приблизительная стоимость одной оценки с учётом всех вызовов.
