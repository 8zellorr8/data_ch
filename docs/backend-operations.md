# Оценки, пакеты, диагностика и отчёты

Это дополнительные возможности backend. Старые маршруты, формула, шкалы, N/A,
цитаты и формат EvaluationRecord сохранены. Frontend и Gemini-клиент не изменены.
Тестовые модели используются только в тестах. Для реального AI по-прежнему нужен
адаптер участника AI; без него запрос оценки и создание пакета дают
`503 AI_NOT_CONFIGURED`.

## 1. Сравнение с ручной разметкой

Подготовьте JSON по `examples/benchmark-manifest.json`. Каждая строка выбирает
конкретный ID ручной оценки, её текущую revision и ID автоматической оценки.
`ai_id: null` разрешён: отсутствие оценки попадёт в пропуски, не в нулевой балл.
Один эталон допускается один раз в отчёте; для сравнения моделей создайте отдельные
манифесты. Ручные эталоны и отчёты с реальными данными храните в игнорируемом `data/`.

```powershell
.\.venv\Scripts\python.exe -m backend.benchmark --database data/cqa.sqlite3 --manifest data/benchmark-manifest.json --output data/quality-report.json
```

Команда только читает SQLite в одной транзакции; AI не вызывается. Сравниваются
одинаковые внутренние ID диалогов, ID/версии чек-листов и снимки входов. Берётся
`original`/`original_score` AI и `final`/`score` ручного эталона указанной revision.
Изменившийся эталон или несовпадающие входы исключаются с явной причиной.
Автоматического выбора «последней» оценки нет.

Результат: совпадения по критериям отдельно для каждой версии правил, ошибочные
N/A, пропущенные N/A, ложные/пропущенные флаги, MAE итогового балла. Флаги с N/A
отдельно исключаются из бинарного сравнения. Итог null исключается из MAE,
но сравнение критериев остаётся. В отчёте есть знаменатели, покрытие и пропуски.
Это внутренние метрики команды, а не официальная формула рейтинга организаторов.
Нужна согласованная ручная разметка; точность реальной модели этим коммитом не измерена.

## 2. Повторные запросы

POST `/api/v1/evaluations` и `/api/v1/evaluations/manual` принимают необязательный
`Idempotency-Key`: 1–128 символов `A-Z a-z 0-9 . _ : -`. Отправляйте новый UUID
для новой намеренной оценки; сохраните его для сетевых повторов той же операции.
Без ключа каждый запрос остаётся новой оценкой. Пространства ключей AI и ручных
оценок раздельны. В БД хранится SHA-256 ключа и нормализованного запроса.

```http
POST /api/v1/evaluations
Content-Type: application/json
Idempotency-Key: 965dd75d-7304-40c0-8722-7c820e0e608c

{"conversation_id":"INTERNAL_UUID","checklist_id":"freedom-broker","checklist_version":1}
```

| Состояние | Ответ |
| --- | --- |
| Первый успешный запрос | 201, обычный EvaluationRecord |
| Тот же ключ и запрос после успеха | 201, исходный сохранённый ответ; AI не вызывается |
| Тот же ключ с другими данными | 409 IDEMPOTENCY_CONFLICT |
| Запрос выполняется | 409 EVALUATION_IN_PROGRESS |
| Предыдущий запуск завершился ошибкой | 409 EVALUATION_FAILED |
| Запуск прерван/истёк срок владельца | 409 EVALUATION_INTERRUPTED |

Повтор возвращает снимок первого ответа, даже после апелляции. Актуальную оценку
читайте через GET `/api/v1/evaluations/{id}`. Автоматического удаления ключей нет.
Прежде чем намеренно повторять неудачный запрос с новым ключом, проверьте историю
и возможный расход у провайдера. Однократность внешнего платного вызова при любых
сбоях не гарантируется.

## 3. Нагрузка и восстановление

`CQA_AI_CONCURRENCY=2` ограничивает число выполняющихся AI-оценок в одном экземпляре
приложения. Обычные запросы и пакетный обработчик используют один ограничитель.
HTTP-запрос без свободного слота получает `503 AI_BUSY`, без неограниченной очереди.
Повтор успешного запроса по ключу не занимает AI-слот. Слот освобождается после
завершения, ошибки, отмены или кооперативного тайм-аута.

Рекомендуемый запуск для демо: один Uvicorn worker. При нескольких workers
лимит умножается на их количество. SQLite атомарно резервирует ключи и захватывает
пакетные задания между процессами; это не распределённый ограничитель квот Gemini.
Квоты запросов/токенов и ограниченные безопасные повторы провайдера — отдельная
задача AI-адаптера. Backend сам не повторяет AI-вызовы.

Каждый процесс имеет UUID владельца с арендой 30 секунд; heartbeat раз в 10 секунд.
Завершившийся штатно процесс помечает свои незавершённые операции `interrupted`.
После аварии новый/живой процесс обнаруживает истёкшую аренду при старте или
heartbeat; до этого статус может оставаться `running`. Просроченный владелец
не может завершить ключевую операцию. Возобновляются только `pending` задания:
ещё не начатые или безопасно отложенные после известного отказа 429 (раздел 10).
`running` после потери владельца не повторяется.
При штатной остановке потребитель получает и явный сигнал остановки, и отмену
задачи: даже если ожидание завершилось одновременно с отменой, новый цикл
обработки не начинается.

Оценка, успешное состояние выполнения, ответ для повтора и успешное состояние
элемента пакета записываются одной транзакцией. Во время вызова AI транзакция не
удерживается. Отмена ожидает окончания уже начатой записи SQLite перед фиксацией
ошибки. Неуспех записи журнала виден в логах; до восстановления состояние может
оставаться незавершённым. Зависший адаптер, игнорирующий отмену, нужно исправить:
тайм-аут asyncio не завершает принудительно чужой процесс/сетевую операцию.

## 4. Диагностика

Ответы, включая 404/422/413/500 и CORS preflight, содержат `X-Request-ID`.
Разрешено передать свой ID с теми же безопасными символами и пределом 128;
некорректный или дублированный заголовок заменяется UUID. После резервирования
AI-запуска ответ также содержит `X-Execution-ID` — он нужен для отчёта о расходе
неудачного запуска. Оба заголовка доступны браузеру через CORS.

Лог `backend.requests`: request ID, метод, шаблон маршрута, статус, миллисекунды,
код ошибки. Для нераспознанного пути используется `<unmatched>`. Тела, реплики,
авторизация, ключ идемпотентности и query не логируются. Стандартный access log
Uvicorn отключается в пользу этого лога; HTTPX URL редактируется целиком.
Внешние proxy/SDK должны отдельно соблюдать те же ограничения.

## 5. Пакетная оценка

POST `/api/v1/evaluation-batches` → 201 BatchRecord:

Для сетевых повторов передавайте `Idempotency-Key` (тот же формат 1–128 безопасных
символов, что у одиночной оценки). Ключ действует в отдельном пространстве пакетов.

```json
{
  "conversation_ids": ["INTERNAL_UUID_1", "INTERNAL_UUID_2"],
  "checklist_id": "freedom-broker",
  "checklist_version": 1
}
```

Версия обязательна. В пакете 1–100 уникальных диалогов. Все ссылки проверяются
до записи. `CQA_BATCH_QUEUE_LIMIT=1000` ограничивает суммарное число pending/running
элементов в базе; переполнение даёт `503 BATCH_QUEUE_FULL`.

GET `/api/v1/evaluation-batches/{id}`:

```json
{
  "id": "BATCH_UUID",
  "created_at": "2026-01-01T00:00:00+00:00",
  "checklist_id": "freedom-broker",
  "checklist_version": 1,
  "completed": false,
  "items": [
    {"id":"ITEM_UUID","conversation_id":"INTERNAL_UUID_1","status":"pending","evaluation_id":null,"error_code":null}
  ]
}
```

Статусы: pending, running, succeeded, failed, interrupted. `completed=true`
означает отсутствие pending/running, а не успех всех элементов. Результат
успешного элемента читается по evaluation_id существующим API. Ошибка одного
элемента не отменяет остальные. Каждый процесс имеет одного последовательного
пакетного потребителя; обычные оценки могут выполняться параллельно в пределах
общего лимита. При AI_BUSY пакетный элемент остаётся pending.

При одинаковом ключе и запросе POST возвращает 201 с тем же ID и исходным снимком
ответа, без новых элементов и вызовов AI. Изменение диалогов, их порядка, чек-листа
или версии с прежним ключом даёт 409 IDEMPOTENCY_CONFLICT. Ключ привязывается только
при успешном создании: ошибка записи, валидации ссылок или заполненная очередь не
оставляют частичный пакет/ключ. Конкурирующие запросы сериализуются транзакцией
SQLite. Хранятся SHA-256 ключа и запроса; исходный ключ в БД/ответы не попадает.

Повтор успешно принятого пакета работает и при заполненной очереди либо временно
отключённом AI. Он не перезапускает failed/interrupted элементы. Актуальные статусы
читайте через GET по ID: повтор POST возвращает исходный снимок с pending.
Без ключа POST сохраняет прежнее поведение: каждый запрос создаёт новый пакет.
Сохраняйте ключ до первого POST и используйте его после обрыва сети; для намеренно
новой оценки нужен новый ключ. Автоматического удаления ключей пока нет.

GET `/api/v1/evaluation-batches?limit=20&offset=0` восстанавливает список после
обновления страницы. `limit` от 1 до 100 (по умолчанию 20), `offset` от 0.
Сортировка: created_at DESC, затем id DESC; одинаковое время не делает порядок
случайным. Пустая страница допустима, total сохраняет число всех пакетов.

```json
{
  "items": [{
    "id": "BATCH_UUID", "created_at": "2026-01-01T00:00:00+00:00",
    "checklist_id": "freedom-broker", "checklist_version": 1,
    "completed": false, "total": 10,
    "pending": 6, "running": 1, "succeeded": 2, "failed": 1, "interrupted": 0
  }],
  "total": 1, "limit": 20, "offset": 0
}
```

Внешний total — число пакетов, total внутри элемента — число его диалогов.
Сводка не содержит транскриптов и полного списка элементов. Счётчики отражают
актуальный снимок БД, включая частичные ошибки. completed означает отсутствие
pending/running, а не успешность всех диалогов. При создании новых пакетов между
запросами offset-страницы могут смещаться: обновляйте первую страницу и объединяйте
элементы по ID. UI списка и прогресса — задача frontend-участника.

## 6. Использование и стоимость

POST `/api/v1/reports/usage`, ровно один способ выбора:

```json
{"evaluation_ids":["EVALUATION_UUID"]}
```

```json
{"execution_ids":["ID_FROM_X_EXECUTION_ID"]}
```

```json
{"batch_id":"BATCH_UUID"}
```

Выбор evaluation_ids покрывает связанные успешные запуски. Для полного расхода
пакета, включая ошибки, используйте batch_id; для одиночной ошибки сохраните
X-Execution-ID. Пропущенные ID отражаются в missing_ids. Старые AI-записи без
журнала читаются по метаданным, но помечаются как неполный учёт. Ручные оценки
не являются источником данных о расходе модели.

Тарифы загружаются при старте из `CQA_TARIFFS_PATH`, пример структуры —
`examples/tariffs.example.json`. В примере вымышленные цены и модель. Укажите
реальные model, currency, version, effective_date, token_unit, input_price,
output_price. Один активный тариф на модель. Каждый отчёт содержит применённый
тариф; это оценка по выбранному тарифу, не исторический счёт провайдера.

Формула: input_tokens × input_price / token_unit + output_tokens × output_price /
token_unit. Арифметика Decimal; деньги сериализуются строками без потери точности.
Разные валюты не складываются. Нет тарифа/токенов — стоимость `null` или известная
часть с `complete=false`. Ноль известных вызовов при `calls_complete=false` не
означает отсутствия расходов.

`known_cost_by_currency`, `known_calls`, `known_input_tokens`, `known_output_tokens`,
`known_duration_ms` показывают известную часть. `complete`, `calls_complete`,
`tokens_complete`, `duration_complete`, limitations и pending_items показывают
границы учёта. Число вызовов адаптера и токены должны включать все его попытки;
backend не умножает уже агрегированные токены на число вызовов повторно.

## Расширение AI-контракта

Старый Evaluator и поля EvaluatorOutput сохранены. Необязательное `usage` принимает
ProviderUsage из backend.work_models: model, calls, input_tokens, output_tokens,
complete. По умолчанию complete=false. Адаптер может установить true только когда
учтены все вызовы, включая повторы, и все оплачиваемые категории выражены двумя
тарифными ставками. Кеш, reasoning, инструменты и прочие категории нельзя молча
выбрасывать; при невозможности точного сведения оставляйте complete=false.

При сбое можно выбросить EvaluatorFailure(code, безопасное_message, usage).
Без такого расширения прежний адаптер продолжает работать, но полнота расхода
не подтверждена. Usage проверяется отдельно от правильности оценок: некорректные
критерии не делают уже выполненный вызов бесплатным. Backend не может узнать
расход на оборванный запрос без данных провайдера.

## 7. Отмена ожидающих элементов

`POST /api/v1/evaluation-batches/{batch_id}/cancel`, без тела. Ответ 200 — актуальный
BatchRecord; неизвестный пакет — стандартный 404 NOT_FOUND. Можно вызывать без AI,
повторять после сетевого сбоя и для уже завершённого пакета. Отмена переводит только
pending в interrupted с `error_code: "BATCH_CANCELLED_BEFORE_START"`.

Захват обработчиком и отмена согласованы блокировкой SQLite. Если захват выиграл,
элемент уже running и запрос его не отменяет. Это не обрыв начатого платного вызова:
running, succeeded, failed и прежние interrupted остаются без изменений. Пакет
может вернуть completed=false, пока running не закончатся. При обычном перезапуске
отменённые элементы не запускаются.

В usage для таких элементов появляется строка `provider_not_called=true`,
`known_cost="0"`, duration=0, `complete=true`, без модели/тарифа. Это известные ноль
вызовов и ноль токенов. Валюта не выдумывается, поэтому для полностью отменённого
пакета `known_cost_by_currency={}` при `complete=true`. Поле provider_not_called
необязательное, по умолчанию false. Для оборванного обращения к модели расход
по-прежнему неизвестен: `known_cost=null`, `calls_complete=false`, если нет usage.
Строки отмены имеют синтетический id с префиксом cancelled-before-start и доступны
при выборе batch_id: это не X-Execution-ID, поскольку вызова и записи исполнения нет.

## 8. Отчёт качества по HTTP

`POST /api/v1/reports/quality` принимает тот же JSON, что benchmark CLI:

```json
{"pairs":[{"reference_id":"MANUAL_ID","reference_revision":1,"ai_id":"AI_ID"}]}
```

От 1 до 1000 пар, каждый reference_id один раз; общая граница тела запроса — 8 MiB.
reference_revision обязателен. `ai_id=null` явно обозначает отсутствие AI-оценки.
Используются только перечисленные записи: сервер не ищет «последнюю подходящую».

API и CLI вызывают один QualityReportService и compare_evaluations. Выбранные
оценки читаются в одном снимке БД. Сравниваются final ручного эталона указанной
актуальной ревизии и original AI, включая original_score. Если эталон пересмотрен,
запрос со старой ревизией получает исключённую пару REFERENCE_REVISION_CHANGED;
сервер не заменяет её новой ревизией и не реконструирует старую автоматически.
Клиент перечитывает историю и явно выбирает нужный актуальный эталон.

Ответ 200 — QualityReport, даже если все пары исключены. `selected`, `compared`,
`missing_or_mismatched`, `coverage` показывают покрытие; `score_compared` —
знаменатель MAE, `score_null_excluded` — сколько пар исключено из MAE из-за null.
`mae` сериализуется строкой Decimal или null. Для каждого критерия есть compared,
matches, accuracy; ошибки N/A и флагов считаются отдельно. `flag_compared` и
`flag_na_excluded` показывают отдельные знаменатели флагов.

Причины в `pairs[].issue`: MISSING_REFERENCE, MISSING_AI, WRONG_ORIGIN,
REFERENCE_REVISION_CHANGED, INPUT_MISMATCH (диалог, версия правил или input_hash).
Пропуски и несовпадения не превращаются в нулевую ошибку. При нулевом покрытии
MAE=null. Отчёт не содержит транскриптов/цитат и не вызывает AI; ручные эталоны
никуда не отправляются. Это внутренние метрики команды, не официальная формула
рейтинга хакатона. До реального AI и ручной разметки точность модели не измерена.

## 9. Резервное копирование

Команды create/verify/restore, ограничения и полностью синтетический временный
пример: [backup-restore.md](backup-restore.md). Для frontend нет HTTP-маршрута
скачивания базы. Восстановленные незавершённые задания требуют ручной проверки:
`interrupted` / `RESTORE_REQUIRES_REVIEW`, без автоматического повтора модели.

## 10. Частота запросов, 429 и продолжение пакета

Настройки процесса (также добавлены в `.env.example` и `.env.docker.example`):

```dotenv
CQA_GEMINI_RPM=3
CQA_BATCH_RATE_RETRIES=3
```

RPM — положительное число запросов в минуту **на модель**, по умолчанию 3:
не чаще одного старта в 20 секунд. Лимитер проверяется перед каждым сетевым
обращением, включая повтор и fallback внутри Gemini-адаптера. В приложениях
`ai.app:app` и `ai.app:create_hosted_app` общий график запросов и cooldown хранятся
в SQLite; одиночная оценка и пакеты используют одну политику. Несколько процессов
с одним файлом БД согласуют разрешения короткими транзакциями. Пауза не держит
транзакцию SQLite и не блокирует event loop. Проверять RPM надо по квоте своего
проекта: значение 3 — консервативная настройка, не утверждение о тарифе Google.

Standalone `ai.check_connection`, benchmark и самостоятельно созданный
`GeminiEvaluator` используют лимитер в памяти. Он ограничивает текущий экземпляр;
разные CLI-процессы, ноутбуки и другие приложения с тем же Google-проектом не
делят эту локальную квоту. Для общего прогона используйте один backend/SQLite.
TPM и RPD заранее не резервируются: это ограничение частоты запросов, а не
система подсчёта всех токенов и суточных обращений проекта Google.

### Что происходит при 429

- Адаптер читает `Retry-After` (секунды или HTTP-date) и `google.rpc.RetryInfo`.
  При нескольких валидных подсказках выбирается самая поздняя. Суточная квота
  определяется по структурированному `QuotaFailure.quotaId`, а не тексту сообщения.
- При известной суточной квоте без корректной подсказки пауза равна 24 часам;
  при обычном 429 без подсказки — 60 секундам. Валидные интервалы от 0 до 366 дней
  принимаются с минимальным ожиданием 1 секунда. Невалидные/бесконечные интервалы
  игнорируются. Сырой ответ провайдера и ключ не выходят в ответы/логи.
- Немедленного повтора или переключения модели после 429 нет. Пауза сохраняется
  на модель в БД. При активном cooldown новые обращения отклоняются локально,
  не расходуя API; в usage это известный ноль `provider_not_called=true`.
- Для отдельной HTTP-оценки сохранён `502 AI_UNAVAILABLE` и прежний JSON ошибки;
  добавлен заголовок `Retry-After`, доступный через CORS. Если использовался
  `Idempotency-Key`, повтор этого ключа по-прежнему возвращает прежний терминальный
  отказ (`409 EVALUATION_FAILED`), а не запускает ещё одну платную попытку.

В пакете известный отказ до генерации результата атомарно сохраняет неуспешную
попытку и возвращает элемент в `pending`. Дополнительные поля элемента:

```json
{
  "id": "ITEM_UUID", "conversation_id": "CONVERSATION_UUID", "status": "pending",
  "evaluation_id": null, "error_code": "AI_QUOTA_EXHAUSTED",
  "retry_at": 1794124800.0, "rate_limit_retries": 1
}
```

`retry_at` — Unix-время UTC в секундах, `null` если ожидания нет.
`rate_limit_retries` — число фактических отказов 429 в текущем бюджете повторов;
локальная пауза без вызова не увеличивает его. `error_code` при ожидании:
`AI_RATE_LIMITED` или `AI_QUOTA_EXHAUSTED`. Набор статусов не изменился;
`completed=false`, пока есть pending/running. После истечения паузы обработчик
продолжает работу автоматически, в том числе после обычного перезапуска.

`CQA_BATCH_RATE_RETRIES` — число **дополнительных** попыток после первого отказа,
целое 0–10. По умолчанию после четвёртого отказа элемент становится `failed`.
Суточный cooldown не превращается в частые короткие повторы. Обычная ошибка,
тайм-аут, отмена и неизвестный исход не получают автоматического повторного
вызова очередью. Если перед 429 внутри адаптера уже была неоднозначная попытка,
элемент также не возобновляется автоматически. Адаптер сохраняет прежние
ограниченные попытки для тайм-аутов/503; очередь не добавляет к ним новые.

### Продолжить тот же пакет

```http
POST /api/v1/evaluation-batches/BATCH_UUID/resume
```

Тело не требуется. Ответ 200 — актуальный BatchRecord; неизвестный ID — стандартный
404, переполненная очередь — 503 BATCH_QUEUE_FULL без частичных изменений.
Операция возвращает в pending **только failed** с `AI_RATE_LIMITED` либо
`AI_QUOTA_EXHAUSTED`, без evaluation_id, и выдаёт им новый бюджет повторов.
Сохранённое время ожидания и cooldown не сбрасываются. Succeeded, running,
уже pending, отменённые и interrupted остаются без изменений. Конкурентные
resume/claim/cancel сериализуются SQLite. Повтор resume уже ожидающего/завершённого
пакета безопасен; после нового исчерпания бюджета ещё один resume является
новым явным запросом продолжения. Не запускайте автоматический цикл resume.

Не создавайте новый пакет со всеми прежними ID ради продолжения: это намеренно
новая оценка и может повторно вызвать модель для готовых диалогов. Сохраняйте
исходный batch_id, читайте GET и используйте resume. Ошибки старой версии
`AI_UNAVAILABLE`, где причина 429 отдельно не сохранялась, автоматически не
классифицируются задним числом. После восстановления backup элементы с
`RESTORE_REQUIRES_REVIEW` тоже не запускаются этим маршрутом.

### Хранение и обновление

Выполнения теперь образуют журнал попыток на элемент: неудачный вызов не
перезаписывается при следующей попытке. Usage по batch_id включает их все,
с отдельным учётом локальных отказов без обращения к модели. Готовая оценка,
статус succeeded и ссылка на неё фиксируются одной транзакцией.

Первый запуск новой версии транзакционно переносит `evaluation_executions`,
убирает ограничение «одна попытка на элемент» и добавляет признак известного
нулевого вызова. ID, история, индексы и триггеры сохраняются; при ошибке изменения
откатываются. Добавлены `provider_limits` и `batch_retry_state`. Перед обновлением
сделайте backup; не запускайте старый и новый код одновременно на одной БД.
Для отката к старой версии используйте предыдущую копию базы: старый код не знает
про несколько попыток. Старые закрытые backups читаются новой версией.

Эти механизмы не увеличивают бесплатную квоту и не измеряют точность Gemini.
Git push не обновляет alwaysdata автоматически — требуется отдельный деплой.
