# Резервная копия и проверка восстановления

Команды выполняются из корня репозитория, отдельно от HTTP-сервера. Новых зависимостей
нет. CLI не запускает FastAPI, потребителя пакетов или AI и не загружает `.env`:
каждый путь задаётся явно. Публичного HTTP-доступа к SQLite-файлам нет.

## Команды

```text
python -m backend.backup create --database LIVE.sqlite3 --output NEW_BACKUP.sqlite3 --timeout 60
python -m backend.backup verify --backup NEW_BACKUP.sqlite3
python -m backend.backup restore --backup NEW_BACKUP.sqlite3 --output NEW_RESTORED.sqlite3
```

Родительский каталог назначения должен существовать. Все имена назначения должны
быть новыми: существующие файлы, каталоги, ссылки и SQLite sidecar-файлы отвергаются.
`restore` не заменяет рабочую БД. Успех выводится JSON и кодом выхода 0; ожидаемая
ошибка — безопасным кодом/описанием в stderr и кодом выхода 1. Неверные аргументы
дают 2. Содержимое диалогов и записей в stdout/stderr не выводится.

`create` использует штатный `sqlite3.Connection.backup`, а не копирование live-файла.
Приложение может продолжать писать в WAL. Лимит `--timeout` относится к получению
снимка; непрерывные записи могут потребовать повторить создание под новым именем.
После копирования журнал переводится в DELETE: резервная копия — один законченный
SQLite-файл, без зависимости от исходных `-wal`/`-shm`.

До публикации проверяются `integrity_check`, `foreign_key_check` и чтение данных
моделями backend: чек-листы, диалоги, оценки с апелляциями, пакеты, сохранённые ответы
идемпотентности и usage. Поддерживается текущая схема backend; чужая SQLite-база или
старая схема без таблиц пакетов отклоняется как `SCHEMA_UNSUPPORTED`, не мигрируется.

Рядом создаётся `NEW_BACKUP.sqlite3.manifest.json` с `format_version`, UTC-датой,
именем файла, размером в байтах и SHA-256. Для переноса сохраняйте оба файла и имя
базы. Файлы публикуются hard link из временных файлов в том же каталоге: это
атомарная публикация каждого законченного файла без перезаписи. Нужна файловая
система с поддержкой hard links (например, NTFS/ext4). Ошибка файловой системы
возвращается явно; небезопасной замены существующего пути нет.

Манифест публикуется последним и обозначает готовность пары. Публикация двух имён
не является одной атомарной операцией: аварийное завершение между ними может
оставить файл без манифеста. `verify`/`restore` такой файл отвергнут. Не исправляйте
его манифест вручную; создайте новую копию с другим именем. SHA-256 обнаруживает
повреждения, но не доказывает происхождение файла.

## Что именно делает restore

1. Читает ограниченный по размеру манифест и копирует backup в приватный временный
   файл. Проверяет размер, SHA-256, целостность, внешние ключи и читаемость истории
   именно этой копии, исключая подмену проверенных байтов последующим чтением.
2. В одной транзакции помечает running-запуски и pending/running-элементы пакетов
   как `interrupted`, с `error_code: "RESTORE_REQUIRES_REVIEW"`. Аренды старых
   владельцев истекают. Завершённые записи, оригиналы оценок, апелляции, ревизии,
   ключи и исходные ответы идемпотентности сохраняются.
3. Повторно проверяет результат, синхронизирует файл и публикует его под новым
   именем. Выводит количества прочитанных записей и приостановленных заданий.

Ожидающие задания тоже приостанавливаются: исходный сервер мог выполнить их
**после** создания backup. Их расход не считается известным нулём. Восстановление
не отменяет вызов, продолжающийся на исходном сервере, и не повторяет его. После
проверки истории и данных провайдера команда самостоятельно решает, какие задания
запустить заново с новыми ключами. Прежний ключ успешного POST возвращает сохранённый
исходный ответ; актуальное состояние пакета всегда читать через GET.

`verify` ничего не приостанавливает и не меняет backup. У копии не должно быть
SQLite sidecars: используйте неизменяемый backup, не открывайте его как рабочую
базу. Восстановленный файл отличается от backup из-за приостановки заданий; старый
манифест к нему неприменим. Для дальнейшего хранения создайте отдельный backup.

Переключение сервера на восстановленный файл выполняется вручную после проверки:
остановите старый экземпляр и укажите новый `CQA_DATABASE_PATH`. Не запускайте два
сервера на исходной и восстановленной базах как один общий сервис.

## Безопасный прогон на временных синтетических данных

PowerShell, из корня репозитория с установленным окружением:

```powershell
$backupDemo = Join-Path ([IO.Path]::GetTempPath()) ("cqa-backup-demo-" + [guid]::NewGuid())
New-Item -ItemType Directory -Path $backupDemo | Out-Null
@'
import sys
from pathlib import Path
from backend.db import Repository
from backend.models import DatasetImport
repo = Repository(Path(sys.argv[1]))
repo.initialize()
repo.import_dataset(DatasetImport.model_validate_json(Path("examples/synthetic-dataset.json").read_bytes()))
'@ | .\.venv\Scripts\python.exe - "$backupDemo/live.sqlite3"
.\.venv\Scripts\python.exe -m backend.backup create --database "$backupDemo/live.sqlite3" --output "$backupDemo/snapshot.sqlite3"
.\.venv\Scripts\python.exe -m backend.backup verify --backup "$backupDemo/snapshot.sqlite3"
.\.venv\Scripts\python.exe -m backend.backup restore --backup "$backupDemo/snapshot.sqlite3" --output "$backupDemo/restored.sqlite3"
```

В выводе verify должны быть ненулевые количества диалогов и версий чек-листов.
Повтор последней команды должен завершиться `DESTINATION_EXISTS`. Рабочие данные
команды в этом примере не используются. Проверки истории, апелляций, конкурентной
записи WAL и запрета повторных AI-вызовов находятся в `tests/integration/test_backup.py`.

Типичные ошибки: `HASH_MISMATCH` — не совпали байты; `INTEGRITY_FAILED` /
`FOREIGN_KEYS_FAILED` / `DATABASE_ERROR` — повреждение SQLite; `INVALID_CONTENT` —
нечитаемый контракт; `FILESYSTEM_ERROR` — нет доступа/каталога/поддержки операции;
`BACKUP_TIMEOUT` — снимок не завершён; `BACKUP_IN_USE` — найдены sidecar-файлы.

Механизм: [SQLite Online Backup API](https://www.sqlite.org/backup.html),
[Python sqlite3.Connection.backup](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup).
